<objective>
实现按需、确定性的 `topic.get` 投影：从已有 Authority 构建 Project、Goal、Decision 的主题上下文，而不建立第二事实库或持久化页面正文。

本计划仍是 inactive v1.5 预规划。实际执行必须等 v1.4 已完成、Authority 读取接口和 evidence resolver 已由真实验收稳定后重新核对。
</objective>

<threat_model>
- 上游 material 可能过期、封存、冲突或版本不匹配；若直接平铺为摘要，会把错误内容伪装为 current。
- 只读汇总层最容易因 convenience 改写数据库、调用 Provider 或向向量索引回灌；必须对读路径做副作用反证。
- 部分 Authority 失败时，返回旧页面或异常详情都会误导用户或泄露实现信息；必须按区块降级并以 code 说明。
- 单次 Outcome 不是因果证明；Decision resolver 必须保持现有 non-causal 表达。
</threat_model>

<tasks>
<task type="execute">
  <name>Task 1: 建立三种 Topic 的 exact read resolver 与 Authority 边界</name>
  <files>src/personal_knowledge/services/topic_projection.py</files>
  <action>
在 `TopicProjectionService` 中实现 `topic.get`：

- `project:{scope}` 只读取 `domain=project` 且 scope 完全匹配的 Personal State assertion，并仅关联显式绑定的 Decision 引用；
- `goal:{domain}:{scope}:{predicate}` 只读取 `assertion_kind=goal` 及三个完全匹配字段，保留 current/history/conflict；
- `decision:{recommendation_id}` 只按 recommendation ID 读取现有 Decision Feedback / Analysis / Pilot chain，并把 recommendation、confirmation/action/outcome reference 及 non-causal limitation 显式展示。

使用现有只读 service/evidence helper 和 `mode=ro`/`query_only` 模式；禁用浏览器端 join、全库扫描和 semantic retrieval。所有跨 Authority 记录必须保留 authority_id、record_type、record_id、snapshot_id、checksum（存在时）等有界 reference。不得为了“主题更丰富”提取或缓存完整原始对话。
  </action>
  <verify>为三种 Topic 准备最小 fixture authority；断言 exact join，不存在近似 key 或同标题记录的隐式归并。</verify>
  <done>每种 P0 topic 都可由 existing Authority 重建，且没有新事实表、实体图、页面表、Provider 或索引写路径。</done>
</task>

<task type="execute">
  <name>Task 2: 形成 snapshot-bound、truthful 的 read envelope</name>
  <files>src/personal_knowledge/services/topic_projection.py</files>
  <action>
按 `personal_wiki_projection_v1` 输出 `generated_at`、canonical topic、`snapshot_bindings`（serving/personal/external/decision）、authority status、`freshness`、`partial`、limitations、data 和 `projection_checksum`。checksum 对 canonical JSON 的已发布 data、依赖 reference 与 bindings 计算，保证同一输入顺序稳定。

把 Current Fact/Observation、Inference/Forecast、Recommendation、Historical/Superseded、Conflict、External 分别放入结构化区块；历史/冲突不得生成 current conclusion，External 不得写入 personal 区。Phase 41 没有持久化页面，成功状态只能是 `fresh`、`partial` 或 `unavailable`；不得出现把旧页叫作 `stale/fresh` 的缓存语义（`stale` 留给 Phase 43）。

Authority 不可用、binding 缺失、checksum/snapshot 不匹配或 privacy seal 时，仅受影响区块降级到 partial/unavailable；返回受限 reason code 与 retryability，服务端详细诊断只记录到既有受控日志，绝不放入 envelope。
  </action>
  <verify>在 fixture 中分别模拟 personal、decision 与 evidence failure、privacy sealing、snapshot mismatch；验证未受影响区块仍可读、受影响区块诚实降级且不出现异常字符串。</verify>
  <done>响应可以说明“已知什么、缺什么、来自哪个快照”，但不能把推断/旧内容/外部事实伪装为当前个人事实。</done>
</task>
